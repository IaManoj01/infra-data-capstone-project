# 8. Database Design and Storage

## 8.1 Introduction

The project uses MySQL as its operational relational database.

The database stores solar farm application data generated by the simulator and accessed by the Spring Boot backend.

In the local environment, MySQL runs inside a Docker container. In production, the application connects to an AWS RDS MySQL database.

## 8.2 Database Technology

| Environment | Database |
|---|---|
| Local development | MySQL 8.0 Docker container |
| Production | AWS RDS for MySQL |

The configured database name is:

```text
solarfarm_db
```

## 8.3 Database Connectivity

The local Docker Compose configuration starts a MySQL service named:

```text
mysql-db
```

The container is named:

```text
solarfarm-mysql
```

The local database uses a named Docker volume:

```text
mysql_data
```

The volume is mounted at:

```text
/var/lib/mysql
```

This preserves database files when the container is stopped or recreated.

In production, the Spring Boot and Python containers connect to the RDS endpoint using environment-based configuration.

## 8.4 Application Data Models

The backend API exposes the following main data models.

### A. Inverter Generation

The generation API response contains:

- Record ID.
- Site ID.
- Inverter ID.
- Timestamp.
- DC power.
- AC power.
- Interval energy.
- Grid voltage.
- Power factor.
- Status flag.

This model represents the generation measurements associated with an inverter.

### B. Weather Observation

The weather API response contains:

- Record ID.
- Site ID.
- Timestamp.
- Solar irradiance.
- Ambient temperature.
- Module temperature.
- Cloud cover percentage.

This model represents environmental observations associated with a site.

### C. Fault Ticket

The fault-ticket API schema contains:

- Ticket ID.
- Timestamp.
- Site ID.
- Inverter ID.
- Fault type.
- Status.
- Notes.

The documented status values are `OPEN`, `IN_PROGRESS`, and `CLOSED`.

These models are based on the generated OpenAPI schema. The physical database table names, column definitions, indexes, foreign keys, and relationship mappings must be confirmed from the entity classes and database schema.

## 8.5 Database Access Through Spring Data JPA

The backend uses Spring Data JPA to interact with MySQL.

The application separates database interaction from REST controller logic through service and repository layers.

At a high level:

```text
REST Controller
       |
       v
Service Layer
       |
       v
Repository Layer
       |
       v
MySQL Database
```

The controller receives the request, the service performs application-level processing, and the repository handles database access.

## 8.6 Local Database Management

Start the MySQL container:

```bash
docker compose up -d mysql-db
```

Check the container:

```bash
docker ps
```

Inspect database logs:

```bash
docker logs solarfarm-mysql
```

Stop the local services:

```bash
docker compose down
```

Stopping the container does not remove the named volume.

**Warning:** Removing the named volume can permanently remove the local database data. Do not run volume-removal commands unless you intentionally want to delete that data.

## 8.7 Production Database

The production database is hosted on AWS RDS.

The production Compose configuration uses environment variables for:

- Database host.
- Database username.
- Database password.
- Database SSL mode.
- Database name.

The production backend configuration uses Hibernate schema validation rather than automatically changing the database schema.

The RDS database is external to the EC2 Docker Compose stack.

## 8.8 Database Security

- Do not commit database passwords.
- Do not expose the production database publicly.
- Restrict RDS network access to the required application environment.
- Use encrypted database connectivity as configured.
- Keep production database configuration outside the Git repository.
- Use persistent storage and backups for production data.
