# 10. AWS Cloud Infrastructure

## 10.1 Introduction

Amazon Web Services (AWS) provides the cloud infrastructure used to host the production application and support the data pipeline.

The project uses AWS compute, database, object storage, messaging, and identity-management services.

## 10.2 AWS Services Used

| AWS Service | Project Usage |
|---|---|
| Amazon EC2 | Hosts the Docker-based production application |
| Amazon RDS for MySQL | Managed production relational database |
| Amazon S3 | Stores exported data files |
| Amazon SQS | Supports messaging in the data-ingestion workflow |
| AWS IAM | Controls permissions for AWS resources |

## 10.3 Amazon EC2

Amazon EC2 provides the virtual server used to host the production application.

The project runs on an EC2 instance using Amazon Linux 2023.

The instance runs Docker and Docker Compose to manage the production services.

The EC2 instance hosts:

- Spring Boot backend container.
- Python scheduler container.
- React frontend container served by Nginx.

The frontend is accessible through the instance's public IP address over HTTP port 80.

The backend listens on port 8080 inside the Docker network and is not directly exposed as a public host port.

## 10.4 Amazon RDS

Amazon RDS for MySQL provides the managed production database.

The backend and Python simulator connect to the RDS instance using environment-based database configuration.

The RDS database is separate from the EC2 Docker Compose stack.

The database is configured for private application connectivity rather than direct public application access.

The actual VPC, subnet, security group, backup, and encryption settings should be documented from the AWS console configuration.

## 10.5 Amazon S3

Amazon S3 is used to store exported data files generated by the ETL workflow.

The Python service uploads data to the configured S3 bucket.

The bucket is also part of the downstream Snowflake ingestion integration.

The exact bucket name, object prefixes, file formats, lifecycle policies, and encryption configuration should be taken from the actual AWS configuration. Do not publish sensitive infrastructure details unnecessarily.

## 10.6 Amazon SQS

Amazon SQS is used as part of the downstream data-ingestion integration.

It supports messaging between the configured AWS storage and Snowflake ingestion components.

The exact queue name, notification configuration, message format, and permissions should be documented from the deployed configuration.

## 10.7 IAM and Instance Role

The production EC2 instance uses the IAM role:

```text
SolarFarm-EC2-Role
```

The role provides the permissions required by the production application to access configured AWS resources.

The production Python container uses the EC2 instance role rather than passing static AWS access keys into the production container.

This avoids embedding long-lived AWS credentials in the production deployment configuration.

The exact permissions attached to the role should be checked before documenting the detailed access policy.

## 10.8 Network and Security Design

The production environment should follow these principles:

- Public access is limited to the frontend entry point.
- The backend API is accessed through the Nginx reverse proxy.
- The backend container is not directly exposed through a public host port.
- RDS access is restricted to the required application environment.
- AWS service permissions are provided through IAM.
- SSH access to EC2 is restricted to trusted sources.
- Database passwords and application secrets remain outside the source repository.

Security group rules should be reviewed before the final project submission.

In particular, avoid leaving SSH access open to all IPv4 addresses (`0.0.0.0/0`) unless there is a deliberate and temporary reason. Prefer restricting it to a trusted source or using an appropriate managed access method.

## 10.10 Operational Verification

Useful checks on the EC2 instance include:

Check the running Docker containers:

```bash
docker ps
```

Check backend health:

```bash
docker exec solarfarm-springboot \
  sh -c 'wget -qO- http://localhost:8080/actuator/health'
```

Check the frontend through the EC2 host:

```bash
curl -I http://localhost/
```

Check the backend API through Nginx:

```bash
curl -i http://localhost/api/generation
```

The API request should be tested against a valid endpoint rather than the `/api/` root path, which is not defined as an endpoint.
